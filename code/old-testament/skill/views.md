# 视图类型图鉴

> 软件表达的所有视图类型,跨域适用性,以及在什么场景下用。
>
> 本文档支撑产品的核心架构判断:**视图 schema 跨域共享,convention 域绑定**(LLVM 模式)。

---

## 一、核心判断

软件工程几十年来,人类用来"表达系统"的方式**基本可枚举**:**约 15-20 种视图**就覆盖所有领域的核心表达需求。

- 视图类型本身**跨域通用**(状态机就是状态机,Web/游戏/嵌入式都用)
- **convention** 域绑定(怎么从代码反推视图、怎么写回代码,完全不同)
- 因此架构应是 **Universal View Schema + Per-Domain Adapter**(类似 LLVM IR + Frontend/Backend)

---

## 二、视图类型全集(15 种)

### 1. **静态结构视图(Structure View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 系统里有什么"东西",怎么组织 |
| **常见形态** | 类图、ER 图、模块图、ECS 组件图、Scene Graph |
| **从代码反推** | 解析类/类型定义、import 关系 |
| **写回代码** | 生成类/类型骨架 |

---

### 2. **类型/Schema 视图(Type Schema View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 数据形状 + 字段约束 |
| **常见形态** | TypeScript types、Zod schema、JSON Schema、Protobuf、struct 定义 |
| **从代码反推** | 解析类型签名(几乎无损) |
| **写回代码** | 生成类型/接口/struct |

---

### 3. **状态机视图(State Machine View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 离散状态 + 转换条件 + 事件 |
| **常见形态** | 状态图、Statechart、Animator Controller |
| **从代码反推** | 解析 XState 定义 / 解析状态枚举和转换函数 |
| **写回代码** | 生成 XState/状态机骨架 |

---

### 4. **流程/序列视图(Flow / Sequence View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 步骤的时序、谁触发谁、分支 |
| **常见形态** | 流程图、序列图、Saga 步骤、Workflow、游戏 Tick 流 |
| **从代码反推** | 解析 flow builder / 函数调用链 |
| **写回代码** | 生成 flow 骨架 |

---

### 5. **数据流视图(Data Flow View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 数据从哪里来,流过哪里,到哪里去 |
| **常见形态** | Pipeline 图、Reactive 流、信号链、ML 训练 pipeline |
| **从代码反推** | 解析数据变换链 / Pipeline builder |
| **写回代码** | 生成 pipeline 骨架 |

---

### 6. **决策表/规则视图(Decision Table View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 业务规则矩阵:在什么条件下做什么 |
| **常见形态** | 决策表、决策树、规则引擎、DMN 标准、伤害计算表 |
| **从代码反推** | 解析 decision builder / 嵌套 if-else 重构 |
| **写回代码** | 生成决策表代码 |

---

### 7. **依赖图视图(Dependency Graph View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 谁依赖谁,扇入扇出 |
| **常见形态** | import graph、服务依赖图、资源依赖图、Scene Graph、Prefab 引用 |
| **从代码反推** | 静态解析 import / require / using / #include |
| **写回代码** | 通常只读,改 import 即可 |

---

### 8. **行为树/AI 决策视图(Behavior Tree View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 复杂条件行为的层级决策 |
| **常见形态** | Behavior Tree(游戏)、Workflow 决策树、复杂条件路由 |
| **从代码反推** | 解析行为树 DSL / 工作流定义 |
| **写回代码** | 生成行为树定义 |

---

### 9. **资源/约束视图(Resource Budget View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 量化资源消耗、限制 |
| **常见形态** | 内存预算、帧时间预算、并发限制、限流配置、GPU 占用 |
| **从代码反推** | 解析配置 + 静态分析 + 运行时 profile |
| **写回代码** | 修改配置文件 |

---

### 10. **生命周期视图(Lifecycle View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 对象/进程/资源何时创建、变化、销毁 |
| **常见形态** | 进程状态图、对象生命周期、组件生命周期、会话超时图 |
| **从代码反推** | 解析构造/析构 / 生命周期 hook |
| **写回代码** | 生成生命周期 hook 骨架 |

---

### 11. **通信视图(Communication View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 谁和谁通信,用什么协议 |
| **常见形态** | API 调用图、消息队列拓扑、事件总线图、网络包流、玩家通信图 |
| **从代码反推** | 解析 RPC / API call / message publish 调用 |
| **写回代码** | 生成 API client / 消息发送骨架 |

---

### 12. **权限/边界视图(Permission View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 谁能做什么 |
| **常见形态** | RBAC 矩阵、ACL、租户隔离图、game permissions、安全域边界 |
| **从代码反推** | 解析 permission decorator / middleware / policy 文件 |
| **写回代码** | 生成 policy 代码 |

---

### 13. **不变量视图(Invariant View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 永远必须成立的约束 |
| **常见形态** | 约束列表、不变量表达式、property test 规约、物理约束、业务规约 |
| **从代码反推** | 解析 @invariant 注解 / property test 定义 |
| **写回代码** | 生成 assert / property test |

---

### 14. **测试场景视图(Test Scenario View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 验证用例:given/when/then |
| **常见形态** | 单元测试列表、property test 描述、回放测试、Gherkin、游戏录像回放 |
| **从代码反推** | 解析测试文件 |
| **写回代码** | 生成测试骨架 |

---

### 15. **架构/分层视图(Architecture View)**

| 项 | 内容 |
|---|---|
| **表达什么** | 系统拓扑、层次、边界 |
| **常见形态** | C4 model、六边形架构图、服务网格、引擎子系统图、游戏引擎层次 |
| **从代码反推** | 解析模块声明 + 依赖关系 + 命名规范 |
| **写回代码** | 通常只读(架构决策来自上层) |

## 五、什么场景下用视图(不是"代码生命周期",是"工程师任务")

| 工程师场景 | 主要用哪类视图 |
|---|---|
| **接手新项目,1 周内要懂业务** | 架构 → 静态结构 → 状态机 → 流程 |
| **修复一个 bug,要先理解相关逻辑** | 数据流 → 状态机 → 决策表 → 不变量 |
| **加新功能,评估影响范围** | 依赖图 → 通信 → 权限 |
| **优化性能,找瓶颈** | 资源/约束 → 数据流 → 通信 |
| **设计安全方案** | 权限/边界 → 通信 → 不变量 |
| **重构,确认重构后行为不变** | 测试场景 → 不变量 → 状态机 |
| **Review 别人代码,理解 PR 业务意图** | 状态机 → 流程 → 决策表 |
| **写技术方案文档** | 架构 → 状态机 → 流程 → 决策表 |
| **给非技术 stakeholder 讲业务** | 用户旅程(流程的子集)→ 决策表 |
| **应对线上故障,debug** | 流程 → 状态机 → 通信 → 不变量 |
| **AI 编程时给 AI 提供上下文** | 类型 → 不变量 → 决策表 |
| **新人入职,onboarding** | 架构 → 静态结构 → 主流程 |

**洞察**:**不同任务用不同视图组合**,产品 UI 应该按"任务"组织,不是按"视图类型"组织。

## 六、跨域通用性的精确判断

| 维度 | 通用性 |
|---|---|
| **视图的概念定义**(什么叫状态机) | **100% 通用**(数学定义不变) |
| **视图的呈现形式**(怎么画状态图) | **80% 通用**(节点+边,基本不变) |
| **从代码反推视图的 convention** | **域绑定**(XState ≠ Unity Animator) |
| **从视图写回代码的 convention** | **域绑定** |
| **视图的相对重要度** | **域差异大** |

**结论**:
- **视图 Schema 跨域共享**(可以做成一份标准)
- **Convention Adapter 每个域单独写**(LLVM 模式)
- **产品 v1 选一个域做透,长期通过 adapter 扩展**

## 七、覆盖率估算

按 "**视图能不能覆盖一个域的核心表达需求**" 估算:

| 域 | 覆盖率 |
|---|---|
| **Web / SaaS** | **90%+** |
| **后端服务** | **90%+** |
| **移动端 App** | **85%** |
| **企业管理系统(CRM/ERP)** | **85%+** |
| **游戏** | **70%**(需补 game-specific 视图如 Shader、Material) |
| **嵌入式/实时** | **75%**(需补时序图、信号波形) |
| **ML 系统** | **65%**(需补实验跟踪、超参) |
| **OS / 驱动 / 系统编程** | **50%**(过于底层) |
| **数据库内核** | **60%** |

**结论**:**覆盖 90% 主流"业务软件开发" 可行**;**覆盖 90% "所有软件" 不可行**。

## 八、产品架构推论(基于上述视图分析)

```
┌────────────────────────────────────────────────┐
│  Universal View Schema(15 种视图的 IR)       │
│  纯数据,跨域通用,版本化                       │
└────────────────────────────────────────────────┘
                  ↑↓
┌────────────────────────────────────────────────┐
│  Adapter Layer(每域一套)                     │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐         │
│  │Web/  │ │Node  │ │Unity │ │UE    │         │
│  │React │ │后端  │ │adapt │ │adapt │         │
│  └──────┘ └──────┘ └──────┘ └──────┘         │
│  ┌──────┐ ┌──────┐ ┌──────┐                  │
│  │Embed │ │ML    │ │Mobile│                  │
│  │adapt │ │adapt │ │adapt │                  │
│  └──────┘ └──────┘ └──────┘                  │
└────────────────────────────────────────────────┘
                  ↑↓
┌────────────────────────────────────────────────┐
│  各域代码(SSoT)                              │
└────────────────────────────────────────────────┘
```

**比喻**:**软件工程的 LLVM**——视图 schema 是 IR,domain adapter 是 frontend/backend。

## 九、MVP 视图选择

v1 选 **Web/SaaS 域**,第一批做这 5 个视图(最高 ROI):

| 优先级 | 视图 | 理由 |
|---|---|---|
| 🥇 | **类型/Schema** | 几乎所有现代 TS 项目都有,convention 现成(Zod / TypeBox) |
| 🥈 | **状态机** | XState 已经做完一半工作,可视化天然 |
| 🥉 | **依赖图** | 静态分析成熟,价值大 |
| 4 | **决策表** | 业务规则的标准表达 |
| 5 | **架构/分层** | 入门级视图,新人 onboarding 必看 |

**5 个视图覆盖 Web/SaaS 60-70% 表达需求**,够 MVP 验证。

## 十、关键策略洞察

1. **视图类型可枚举,数量有限**(~15 种)
2. **跨域通用的是 Schema,域绑定的是 Adapter**(LLVM 模式)
3. **不同领域用不同的"重点视图组合"**,产品 UI 要按"任务"而非"视图类型"组织
